# ROADMAP.md

# Nera Roadmap

**Version:** 1.0
**Status:** Approved (Milestone 1 content). Milestones 2+ are planned and subject to the exit criteria of the milestone before them.

> This roadmap is milestone-based. Each milestone contains an ordered list of sprints (`P0xx`). A sprint number is only assigned once its milestone is active — sprint scopes beyond the next milestone are directional, not final.
>
> Platform engines and business modules are kept in clearly separate milestones: **Milestone 2 builds platform engines. Milestone 3 builds the first business modules on top of them.** This order is deliberate — see `NERA_CONSTITUTION.md` Section 3 ("Platform First") and Section 12 (forbidden: building business-module logic before the required core engines exist).

# 3. Milestone 2 — Architecture Finalization & Platform Core

**Objective:** Close every architectural gap identified in Milestone 1 and stand up the platform engines that every future business module depends on: identity, authorization enforcement, audit, events, tenant isolation, and persistence for the existing Entity/Configuration domain model. No business module is built in this milestone.

**Why this milestone exists before any business module:** `NERA_CONSTITUTION.md` forbids building business-module logic before the required core engines exist. Today, Authentication is a demo stub, Authorization is enforced only client-side (and is explicitly documented in its own source as not a security boundary), the `audit_logs` table has no writer, no event bus exists, and there is no API layer at all. None of that can be inherited "for free" by a business module — it must exist first.

**Sequencing note (post-P008):** P008 delivered platform architecture only (Engine Registry, contracts, plugin skeleton — see the P008 row below and ADR-009/010), not a real Identity/Authentication implementation. That means real Identity/Authentication is still unbuilt and **not yet assigned a sprint number.** This note originally argued that a real Identity/Authentication sprint must be scheduled before P011 starts, since Authorization cannot meaningfully enforce _what_ an actor may do without first knowing _who_ the actor is. **Owner decision (P011 planning):** proceed with P011 now rather than inserting an unscheduled Identity/Authentication sprint first, scoping P011 exactly like P010 — a real, tested, Prisma-backed engine with zero real callers wired into `apps/web`, deferring actual request-path enforcement until real Identity/Authentication exists. Real Identity/Authentication (replacing `demoAuth.ts`, which requires its own provider-vendor ADR first — see Section 9.3) remains unscheduled and is still a prerequisite for wiring any real caller into `checkPermission()`.

**Exit criteria for Milestone 2:**

1. A user authenticates for real; there is no code path that reaches protected data without a valid, server-verified session.
2. Every authorization decision is enforced server-side and is independently auditable.
3. Every meaningful mutation writes an audit record and emits a domain event, verified by test, not just by code review.
4. Two organizations cannot see each other's data — verified by an explicit automated RLS test keyed on `organization_id` (ADR-002). Where institutions are used, one organization's institutions are never reachable from another organization's `institution_id` lookups.
5. The Contacts module operates against real persisted data with no data loss on refresh or across sessions.
6. CI blocks a PR that fails lint, typecheck, or tests.

**Objective:** Deliver the full flow `Supplier → Purchase Order → Invoice → Payment Approval → MASAV → Mark Paid → Store Documents`, end to end, on real data. This is the first milestone that produces business modules under `modules/`.

**Why this milestone is next:** Per `PRODUCT_VISION.md` Section 6, Suppliers and Finance are explicitly the first areas meant to make Nera "feel alive." Every other V1 module (Reporting, Forms, Search) is downstream of this data existing.

# 5. Milestone 4 — V1 Completion: Reporting, Forms, Search

**Objective:** Complete the remaining V1 scope items from `PRODUCT_VISION.md` Section 4, all of which are consumers of the real data Milestone 3 now produces.

**Why this milestone is next, not earlier:** Building Reporting or Search before Milestone 3's modules exist would mean designing against no real data — a documented anti-pattern (see `NERA_CONSTITUTION.md` Section 12, "building a generic engine ahead of a real, justified need for it").

1. Reports return correct, tenant-scoped, permission-filtered results against real Milestone 3 data.
2. A submitted form's data is stored, auditable, and retrievable.
3. Global Search never returns a result the searching user is not authorized to see.

# 7. Post-V1 — Future Milestones (Not Scheduled)

These are explicitly deferred by `PRODUCT_VISION.md` Section 5, or newly introduced by this blueprint as future work. They are listed so the roadmap doesn't need to be renegotiated when they come up, not because they are committed to a date.

- **Employees module** — reuses the Entity + role + module-profile pattern proven by Suppliers.
- **Students module**, **Avreichim module** — both depend on the Finance core proven in Milestone 3; both carry institution-specific terminology that must stay inside the module.

# 9. Open Decisions

Milestone 1 surfaced several contradictions between early product direction, the existing repository, and prior documentation. The owner has since resolved some of them directly (recorded as `Accepted` ADRs in `docs/adr/`); others remain genuinely open and are P008's job to close, not this milestone's. This section separates the two so Milestone 2 starts from a precise list rather than rediscovering anything mid-sprint.

## 9.1 Resolved in Milestone 1 (see the cited ADR — no further debate needed)

1. **Organization vs. Institution** — **resolved by ADR-002.** Organization is the tenant and security boundary; RLS remains keyed on `organization_id`. Institution is an optional business hierarchy _below_ Organization, never a substitute tenant boundary; `institution_id`, where used, is always validated against organization ownership. No schema change has been made yet — implementing this (an `institutions` table, optional `institution_id` columns, the RLS/ownership-check pattern) is scheduled as its own future sprint (candidate: P012, "Organization / Institution Engine"), not decided by this roadmap entry alone.
2. **Package naming** — **resolved: no renames.** The existing package names (`packages/database`, `packages/types`, `packages/ui`, etc.) remain authoritative and are not renamed to `packages/db`/`packages/core`/`packages/ui-kit`. A future `packages/core` package may be _added_ (not substituted in) later, but only once it has a clearly defined responsibility not already owned by `packages/types` or `packages/engines` — and only via its own ADR when that need is real, not speculatively now.
3. **UUID version** — **resolved: no migration.** The repository's currently implemented UUID strategy (Prisma's default `uuid()`, i.e. UUIDv4) is the source of truth and is not changed in Milestone 1 or by this roadmap. UUIDv7 remains a candidate future decision, requiring its own ADR plus a migration analysis, before it is adopted for any table, new or existing.
4. **`docs/PROJECT_VISION.md` vs. `docs/PRODUCT_VISION.md`** — **resolved which is canonical: `docs/PRODUCT_VISION.md`**, by owner decision. `docs/PROJECT_VISION.md` is explicitly **not** deleted or rewritten in Milestone 1. **Deprecation/merge note:** `docs/PROJECT_VISION.md` must be reviewed against `docs/PRODUCT_VISION.md` and merged (bringing forward anything not already captured) before it is removed, as its own later approved documentation-cleanup milestone — not implicitly, and not as a side effect of any other sprint.

## 9.2 Resolved in P008 (mechanism only — see ADR-009, ADR-010)

1. **How a provider will be plugged in, once one is chosen.** P008 built the `DatabaseProvider`/`AuthProvider`/`StorageProvider` contracts and a register/resolve mechanism in `@nera/core` (ADR-010). This resolves _how_ a future provider connects to the platform. It does **not** resolve _which_ provider — see 9.3 below, still fully open.

## 9.3 Still Open — Requires Its Own Future ADR

1. **Database / ORM / authentication / storage provider — which vendor.** Prior product input mentioned Supabase, Drizzle, Better Auth, and MinIO as a possible direction; **none of these is adopted, confirmed, or rejected by this document.** The repository's actual, implemented, confirmed tooling today is Prisma (`packages/database`) against a self-hosted-style PostgreSQL target, per `TECH_STACK.md` — that remains the source of truth **until a dedicated ADR is approved.** P008 deliberately did not resolve this (see ADR-009): even binding the already-implemented Prisma client behind the new `DatabaseProvider` contract was ruled out for P008, since it would have added a dependency edge to `packages/database`. A future sprint must formally inspect and decide the stack differences (Prisma vs. any alternative; the authentication provider; the storage provider) before any migration or provider binding, and must produce that ADR first. Until then, every document in this blueprint uses provider-neutral language for anything not already implemented.

## 9.4 Still Open — Prerequisite Before Any Real `apps/web` Caller of a Database-Backed Engine (packaging defect, no ADR required)

1. **Monorepo package-consumption strategy is not compatible with `apps/web`'s bundler once a package barrel statically reaches `@nera/database`.** Discovered during P011 (Authorization Engine — Server Enforcement), while wiring the new `checkPermission()` into `packages/engines/authorization/src/index.ts`'s barrel export: `@nera/database` is written for Node's `NodeNext` module resolution (`packages/database/tsconfig.json`'s `"module"`/`"moduleResolution": "NodeNext"`), which requires relative imports written with a `.js` extension (e.g. `export { prisma } from './client.js'`) even though only `client.ts` exists — a convention only TypeScript's own `NodeNext` resolver (and Node's native ESM loader, once compiled) understands how to map back to the real file. Every workspace package's `package.json` (`@nera/database`, `@nera/authorization-engine`, `@nera/audit-engine`, etc.) points `main`/`types` directly at `./src/index.ts` — none ships a compiled `dist/` — so `apps/web`'s Next.js build consumes this raw source directly through webpack, whose resolver does not understand the `NodeNext` `.js`→`.ts` convention and is not configured (via `resolve.extensionAlias` or `transpilePackages`) to bridge it. The result: any `apps/web` module that statically imports a package whose export graph reaches `@nera/database` fails to build with `Module not found: Can't resolve './client.js'`, regardless of whether the reachable code is actually used (webpack must resolve every statically reachable module before tree-shaking can decide what to drop from the output — an unused re-export is resolved just the same as a used one).
2. **This is a packaging defect, not an authorization-logic defect and not a new architectural decision** — it does not require an ADR (no new tenant/security boundary, provider, or Core Engine is involved; see `NERA_CONSTITUTION.md` Section 9.7's definition of what requires one). It affects `@nera/audit-engine` identically (same `@nera/audit-engine → @nera/database` dependency shape) and will affect any future database-backed engine the same way; it has simply never been exercised yet, because no engine reachable from `apps/web`'s bundle has depended on `@nera/database` until P011's `checkPermission()`. P011 worked around it locally, for itself only, by not re-exporting `checkPermission` through `packages/engines/authorization/src/index.ts`'s barrel — that is a scoped, temporary avoidance, not a fix, and does not resolve this item.
3. **Must be fixed before the first real `apps/web` caller imports any database-backed engine** — real Identity/Authentication, or whichever sprint first wires a genuine server-side caller into `apps/web` (Authorization's `checkPermission()` included), cannot do so until this is resolved. No technical solution is prescribed here; candidate directions exist (e.g., changing `@nera/database`'s own module specifiers, teaching `apps/web`'s bundler the `NodeNext` convention, or giving workspace packages real compiled build output) but none is evaluated, chosen, or authorized by this entry — that evaluation is the responsibility of whichever future sprint depends on it, scoped on its own, not folded into an unrelated engine sprint.
4. **P013A clarification (verified, not a resolution of this item):** P013A's Server Actions (`apps/web/src/lib/actions/entityActions.ts`, etc.) _do_ successfully import `@nera/entity-engine`'s barrel, which reaches `@nera/database` — without hitting this defect. Verified reason: the defect is specific to `apps/web`'s **client-side webpack bundle**; `'use server'` files are never bundled into it. `@nera/authorization-engine`'s barrel still deliberately omits `checkPermission` for the same reason this item describes, because `AuthorizationContext.tsx` (a `'use client'` file) imports that same barrel directly. **This item therefore remains open specifically for any future `'use client'` file that needs to import a barrel reaching `@nera/database`** — it is not resolved by P013A, and P013A did not attempt to resolve it.

## 9.5 Still Open — Surfaced by P013A

Real gaps discovered or confirmed while implementing and reviewing P013A. None are resolved by this roadmap entry; each requires either a future ADR or a future scoped sprint, per `NERA_CONSTITUTION.md` §9.7/§9.8.

1. **Institution application CRUD/management.** Institution is a real, persisted model (P012 — `institutions` table, `FORCE ROW LEVEL SECURITY`, `assertInstitutionBelongsToOrganization`), but no repository, Server Action, or UI exists to create, read, update, or archive an Institution. Every Institution row in the database today exists only via administrative-client test fixtures (`prisma.institution.create(...)` in test files). Not scheduled to any sprint number yet.
2. **Entity-to-Institution ownership/assignment decision.** `Entity`/`PersonProfile`/`Phone`/`Email`/`Address` carry `organization_id` only; none carries `institution_id`. Whether, and how, an Entity should optionally belong to a specific Institution within its Organization is a real product/architecture question that has not been asked of, or decided by, the Owner. Per `NERA_CONSTITUTION.md` §9.8, this is not to be decided unilaterally by a future implementation session — it requires its own ADR (parallel to ADR-002's own precedent) once there is a real, justified need for it (per `NERA_CONSTITUTION.md` §12's anti-overengineering principle).
3. **Branch/Department/Institution/`PermissionScope` naming reconciliation.** ADR-008's hierarchy (`Organization → Branch → Department → Role → User`) and ADR-002's hierarchy (`Organization → Institution`) both place Organization at the top and do not contradict each other there — but whether `Branch`/`Department` and `Institution` are the same concept, nested concepts, or genuinely separate hierarchies is unresolved. `ENGINE_MAP.md` §2's P011 "scope-naming reconciliation" note is deliberately narrow (it only documents that the pre-existing `PermissionScope` enum's `'institution'` value currently means Organization) and explicitly does not resolve this broader question. ADR-008's own Follow-up Actions name this as needing a future ADR; none has been written. Tracked here, per the Owner's instruction, rather than by editing ADR-008 itself.
4. **Real authentication/provider decision — already tracked, not duplicated here.** See §9.3 above (database/ORM/authentication/storage provider — which vendor). No change to that entry was needed; it already covers this gap.
5. **Workspace barrel/client-bundle packaging defect — already tracked, not duplicated here.** See §9.4 above, including its new item 4 recording what P013A confirmed about the defect's actual scope.
